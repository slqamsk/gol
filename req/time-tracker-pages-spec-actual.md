# GOL - Gamification of life - Требования к страницам
Имя файла: `time-tracker-pages-spec.md`

## 01. Введение. Общие технические требования для всех страниц

**FR.01.01.** Все страницы работают полностью на клиенте (HTML/CSS/JS), без серверных запросов.

**FR.01.01.01.** Все данные хранятся в `localStorage`:
Ключ: `time-tracker-categories` - справочник активностей – структура соответствует `TimeTrackerData`.
Ключ: `time-tracker-schedules` - расписания – структура соответствует `SchedulesRoot`.

**FR.01.01.02.** При отсутствии или невалидности обязательных данных страницы должны показывать понятное сообщение об ошибке и (при необходимости) блокировать основной функционал.

**FR.01.01.03.** Статические стили (CSS) выносятся во внешние файлы. Для всех страниц используется общий файл `main.css` (содержит базовую стилизацию, общие классы, таблицы, модальные окна и т.п.). В HTML-файлах присутствуют только ссылки на этот файл через `<link rel="stylesheet">`. Динамические стили (цвет фона, положение блоков и т.п.) устанавливаются через JavaScript.

**FR.01.01.04.** JavaScript-код может быть организован в несколько файлов для удобства разработки и сопровождения (решение о количестве файлов принимает разработчик). Для страницы редактора цветов требуется обязательное разделение: `color-data.js` (массив цветов палитры) и `editor.js` (основная логика). Для страницы дневного трекера такого обязательного разделения нет.

**FR.01.01.05.** Оформление обеих страниц – светлое, без переключения тем.

**FR.01.01.06.** Вёрстка рассчитана на разрешение экрана 2560px по ширине. При нехватке места в окне браузера появляются горизонтальная и вертикальная полосы прокрутки у всей страницы. Запрещается использование медиа-запросов.

**FR.01.01.07.** Прототип не выполняет автоматическую миграцию данных из предыдущих версий. При загрузке невалидных данных пользователь получает сообщение об ошибке и может исправить их вручную через редактор JSON на странице импорта/экспорта.

**FR.01.01.08.** Все временные значения в системе (начало, конец, дельта, перерывы) хранятся и обрабатываются с точностью до минуты. При получении текущего системного времени секунды отбрасываются (округление вниз до целой минуты). При вводе времени пользователем через поле `HH:MM` секунды не допускаются.

## 02. Главная страница (`index.html`)

### 02.01. Назначение

**FR.02.01.** Страница выполняет роль информационного портала и единой точки входа в систему Time Tracker. Она содержит общее описание методологии геймификации жизни, правила работы с учётом времени и ссылки на функциональные страницы приложения.

### 02.02. Структура и содержимое

Страница должна включать:
**FR.02.02.01.** Заголовок и краткое описание проекта «Геймификация жизни».
**FR.02.02.02.** Основные правила расчёта баланса дня (формула, весовые коэффициенты, ставки) – выжимка из `_service_context` справочника.
**FR.02.02.03.** Рекомендации по использованию: как создавать активности, как интерпретировать статусы, как работают перерывы.
**FR.02.02.04.** Навигационное меню со ссылками на следующие страницы (все ссылки открываются в новой вкладке, `target="_blank"`):
  - Редактор справочника (`editor.html`) – для просмотра и изменения цветов рангов и категорий.
  - Загрузка и выгрузка расписаний (`import-export.html`) – страница для ручного экспорта/импорта JSON расписаний.
  - Архивация расписаний (`archive.html`) – страница для просмотра всех сохранённых расписаний и создания резервной копии.
  - Основной трекер (`daily-tracker.html`) – для планирования дня, учёта активностей и визуализации временной шкалы.

### 02.03. Стилизация

**FR.02.03.01.** Страница использует общий файл стилей `main.css`. Дополнительные стили для `index.html` должны быть минимальными и не нарушать общую систему (фиксированная ширина, отсутствие адаптивности).

## 03. Редактор цветов справочника (`editor.html`)

### 03.01. Назначение

**FR.03.01.** Страница позволяет:
- **FR.03.01.01.** **Вставить** содержимое файла `time-tracker-categories.json` в текстовое поле и сохранить его в `localStorage` браузера.
- **FR.03.01.02.** **Просматривать** иерархию «ранги – категории» с визуальным отображением цветов.
- **FR.03.01.03.** **Выбирать и менять** цвета для рангов и категорий через интерактивную палитру.
- **FR.03.01.04.** Все изменения автоматически сохраняются в `localStorage` и отображаются в текстовом поле JSON.

### 03.02. Загрузка и сохранение данных (только через вставку)

**FR.03.02.01.** При открытии страницы код проверяет `localStorage` по ключу `time-tracker-categories`.
- Если данные есть и являются валидным JSON (содержат массив `ranks`), они загружаются, отображаются в текстовом поле и используются для построения таблицы.
- Если данных нет или они невалидны, текстовое поле пустое, таблица пуста (или показывает надпись «Нет данных»). Пользователь должен вставить JSON вручную.

**FR.03.02.02.** Пользователь **вручную вставляет** содержимое JSON в текстовое поле (никакой кнопки «Загрузить файл» нет).

**FR.03.02.03.** По нажатию кнопки **«Применить»** страница парсит содержимое текстового поля. При успехе:
- данные заменяют текущую структуру в памяти;
- сохраняются в `localStorage`;
- перерисовывается таблица;
- в отдельном поле статуса появляется зелёное сообщение: «Данные применены».

**FR.03.02.04.** При ошибке (невалидный JSON, отсутствие массива `ranks`) – красное сообщение с описанием ошибки. Таблица и сохранённые данные не меняются.

### 03.03. Построение иерархии для отображения

**FR.03.03.01.** Исходные данные имеют плоскую структуру: корневые массивы `ranks` и `categories`.

**FR.03.03.02.** Для построения таблицы страница группирует категории по полю `rank_id`. Для каждого ранга формируется список категорий, у которых `category.rank_id === rank.id`.

**FR.03.03.03.** Редактирование цветов происходит непосредственно в плоских массивах (`ranks` и `categories`). При сохранении структура остаётся плоской (никакие вложенные массивы не создаются).

### 03.04. Отображение таблицы

**FR.03.04.01.** Таблица состоит из двух колонок: **Ранги** и **Категории**.

#### 03.04.01. Ячейка ранга

**FR.03.04.02.** Ячейка ранга:
- Содержит `id. Название ранга` (например, `1. Творческие`).
- Показывает английское имя цвета (например, `DarkOrchid`) и **русское название цвета** (например, «Тёмная орхидея»).
- Фон ячейки равен значению `rank.color` (поле `color` у ранга обязательно).

#### 03.04.02. Ячейка категории

**FR.03.04.03.** Ячейка категории:
- Содержит `id. Название категории`.
- **Если у категории есть собственное поле `color`:**
   - Фон ячейки равен этому цвету.
   - В подписи показываются английское имя и русское название цвета.
- **Если у категории нет поля `color`:**
   - Фон ячейки равен цвету **родительского ранга**.
   - В подписи не показывается никакой информации о цвете – только `id. Название категории`.
   - Поле `color` в JSON не создаётся.

#### 03.04.03. Объединение строк для ранга

**FR.03.04.04.** Для каждого ранга, у которого есть хотя бы одна категория, ячейка ранга в первой колонке должна занимать **столько строк, сколько категорий у этого ранга** (атрибут `rowspan`).

**FR.03.04.05.** Если у ранга нет категорий, ячейка ранга занимает одну строку, а во второй колонке отображается текст «Нет категорий» (или ячейка остаётся пустой).

**FR.03.04.06.** Объединение строк выполняется только при рендеринге таблицы; исходные данные при этом не изменяются.

#### 03.04.04. Стилизация таблицы

**FR.03.04.07.** Таблица должна быть **не шире содержимого** (ширина автоматическая, без принудительного растяжения на 100% родителя).

**FR.03.04.08.** Таблица должна выравниваться **по центру страницы** (например, через `margin: 0 auto` для таблицы или через flex-контейнер).

**FR.03.04.09.** Нужно задать минимальную ширину колонок, чтобы избежать слишком узких ячеек: 300px.

**FR.03.04.10.** Все ячейки таблицы (как заголовки, так и обычные) должны иметь **одинаковые границы** (border) одинаковой толщины и стиля.

**FR.03.04.11.** Цвет границы – чёрный.

**FR.03.04.12.** Границы должны быть сплошными (`solid`) и тонкими.

#### 03.04.05. Открытие модального окна

**FR.03.04.13.** При клике на любую ячейку (ранг или категория) открывается модальное окно выбора цвета.

### 03.05. Выбор цвета через палитру

**FR.03.05.01.** Модальное окно содержит сгруппированную таблицу стандартных именованных цветов CSS (английское имя, русское название). Каждая строка имеет фон, соответствующий цвету.
Палитра содержит только стандартные именованные цвета CSS (например, DarkOrchid, Peru). Это позволяет при ручном редактировании JSON (на странице импорта/экспорта или в любом текстовом редакторе) быстро идентифицировать цвет по его английскому имени, не прибегая к справочнику HEX-кодов. HEX-коды не используются, так как снижают читаемость JSON и усложняют ручную правку.

**FR.03.05.02.** При клике на строку палитры:
- Выбранное английское имя цвета сохраняется:
   - **Для ранга** – в поле `rank.color` (обязательное поле, перезаписывается).
   - **Для категории** – **добавляется** поле `category.color` (если его не было).
- Обновляются внутренние данные (плоские массивы), текстовое поле JSON, перерисовывается таблица.
- Данные сохраняются в `localStorage`.
- В поле статуса выводится зелёное сообщение: **«Цвет успешно изменён для ранга „Название ранга“»** или **«Цвет успешно изменён для категории „Название категории“»**.
- Модальное окно закрывается.

**FR.03.05.03.** В палитре предусмотрена **опция «Сбросить (убрать собственный цвет)»** только для категорий (отдельная кнопка или пункт). При её выборе:
- Если у категории есть собственное поле `color`, оно **удаляется** из объекта категории.
- Категория снова отображается с цветом родительского ранга, а в подписи пропадает информация о цвете (остаётся только `id. Название`).
- Изменения сохраняются в JSON (поле `color` исчезает), в `localStorage` и в текстовом поле.
- Для ранга такой опции нет, так как цвет ранга обязателен.

**FR.03.05.04.** Допускается, чтобы один и тот же цвет (например, `Red`, `Gray`, `Blue` и т.д.) присутствовал в нескольких группах палитры (например, и в «Основные цвета», и в «Красные тона», и в «Серые тона»). Это не является ошибкой и упрощает поиск.

### 03.06. Управление сообщениями (статус)

**FR.03.06.01.** На странице есть **отдельное поле (блок) для сообщений** (например, `<div id="status-box">`).

**FR.03.06.02.** Сообщение появляется в этом поле и **остаётся там до тех пор, пока не будет заменено другим сообщением** (не исчезает автоматически).

**FR.03.06.03.** Цвет сообщения:
- **зелёный** – успешная операция (применение JSON, изменение цвета);
- **красный** – ошибка (невалидный JSON, отсутствие `ranks`).

**FR.03.06.04.** При успешном применении JSON выводится: «Данные применены».

**FR.03.06.05.** При успешном изменении цвета: «Цвет успешно изменён для ранга „X“» или «Цвет успешно изменён для категории „Y“».

**FR.03.06.06.** Каждое новое сообщение полностью заменяет предыдущее.

### 03.07. Технические замечания (специфичные для редактора)

**FR.03.07.01.** Палитра использует только стандартные именованные цвета CSS. В JSON сохраняется именно английское имя цвета (например, `"DarkOrchid"`), HEX не допускаются.

**FR.03.07.02.** Код страницы **не должен** изменять массивы `activity_types` и объект `_service_context` – они остаются нетронутыми.

**FR.03.07.03.** При любых операциях с цветами структура JSON остаётся корректной: корневые массивы `ranks`, `categories`, `activity_types` сохраняются плоскими.

**FR.03.07.04.** Пользователь (человек-редактор) может свободно изменять текстовое поле вручную – страница только реагирует на нажатие «Применить» и на клики по ячейкам таблицы.

**FR.03.07.05.** JavaScript-код **обязательно** разделяется на:
- `color-data.js` – содержит только массив `COLOR_GROUPS` (или аналогичную структуру с цветами палитры, их русскими названиями и HEX-кодами).
- `editor.js` – основной код приложения: загрузка/сохранение localStorage, рендер таблицы, обработка кликов, модальное окно и т.д.

**FR.03.07.06.** В HTML-файле должны быть подключены все JS-файлы в правильном порядке.

## 04. Страница загрузки/выгрузки расписаний (`import-export.html`)

**FR.04.01. Назначение**  
Страница предоставляет интерфейс для ручного экспорта и импорта расписаний в/из `localStorage`. Позволяет:
- просматривать список дат, присутствующих в хранилище;
- загружать расписание одной даты или нескольких выбранных дат в текстовый редактор в формате JSON;
- применять отредактированный JSON для замены или добавления расписаний;
- в случае невалидных данных в `localStorage` – загрузить их в редактор для внешнего исправления.

**FR.04.02. Основные элементы интерфейса**  
- Многострочное текстовое поле (`<textarea>`) для отображения и редактирования JSON. Поле имеет фиксированную начальную ширину (например, 800px) и высоту 400px, моноширинный шрифт. Поле можно растягивать и сжимать мышью (resize: both).  
- Блок для вывода статуса (над текстовым полем или под ним, но чётко выделен).  
- Под текстовым полем – таблица (или список) дат с чекбоксами, кнопки управления выбранными датами и кнопки действий.  
- Кнопки: «Загрузить одну дату», «Загрузить выбранные даты», «Применить одну дату», «Применить несколько дат», «Выбрать все», «Сбросить все», «Очистить редактор», «Обновить список дат».

**FR.04.03. Инициализация и отображение списка дат**  
**FR.04.03.01.** При загрузке страница читает из `localStorage` ключ `time-tracker-schedules`.  
**FR.04.03.02.** Если ключ отсутствует – создаётся пустой объект типа `SchedulesRoot` (`{ current_datetime: getCurrentDateTimeString(), schedules: [] }`, где `getCurrentDateTimeString()` возвращает строку в формате ISO 8601 с часовым поясом +03:00 (московское время)) и сохраняется в `localStorage`. В поле статуса выводится зелёное сообщение: «В localStorage не было расписаний – создан пустой объект».  
**FR.04.03.03.** Если ключ существует, выполняется проверка на соответствие типу `SchedulesRoot` (наличие обязательных полей `current_datetime` и `schedules`, а также валидность каждого `ScheduleEntry` – поле `date` в формате YYYY-MM-DD, поле `schedule` – объект с массивом `activities`, и поле `current_datetime` (строка в формате ISO 8601) в самом `ScheduleEntry`). Каждый `ActivityEntry` должен соответствовать спецификации.  
**FR.04.03.04.** Если данные **не соответствуют** ожидаемой структуре:  
- в поле статуса выводится красное сообщение с описанием ошибки;  
- содержимое `localStorage` по ключу `time-tracker-schedules` (в том виде, как оно есть) загружается в текстовое поле редактора (форматирование – табуляция, `JSON.stringify(data, null, "\t")`), чтобы пользователь мог скопировать его, исправить во внешнем редакторе и загрузить обратно через кнопку «Применить одну дату» или «Применить несколько дат».  
- кнопки «Загрузить одну дату», «Загрузить выбранные даты», «Применить одну дату», «Применить несколько дат» остаются активными (пользователь должен иметь возможность исправить данные).  
**FR.04.03.05.** Если данные валидны, массив `schedules` сортируется по полю `date` по возрастанию (от старых к новым) и сохраняется обратно в `localStorage`.  
**FR.04.03.06.** Под текстовым полем выводится таблица (или список) всех дат из `schedules` (уже отсортированных). Для каждой даты отображается чекбокс.  
**FR.04.03.07.** Рядом со списком дат размещаются кнопки «Выбрать все» и «Сбросить все», которые управляют чекбоксами.

**FR.04.04. Загрузка данных в редактор**  
**FR.04.04.01.** Кнопка **«Загрузить одну дату»**:  
- проверяет, что выбран ровно один чекбокс; иначе – сообщение об ошибке в статус (красное).  
- **перед загрузкой обновляет поле `current_datetime` для выбранной даты в самом хранилище на текущее время (считая экспорт взаимодействием) и сохраняет изменения**.  
- загружает из `localStorage` соответствующий `ScheduleEntry` (объект с полями `date`, `schedule` и `current_datetime`) и отображает его в текстовом поле в отформатированном виде (`JSON.stringify(entry, null, "\t")` – табуляция).  
- в статус выводится зелёное сообщение: «Загружено расписание для даты YYYY-MM-DD».  

**FR.04.04.02.** Кнопка **«Загрузить выбранные даты»**:  
- проверяет, что выбрано минимум два чекбокса; иначе – сообщение об ошибке.  
- **перед загрузкой обновляет поле `current_datetime` для каждой выбранной даты в хранилище на текущее время и сохраняет изменения.**  
- формирует массив `ScheduleEntry[]` из выбранных дат (сохраняя порядок возрастания дат).  
- отображает этот массив в текстовом поле (`JSON.stringify(array, null, "\t")`).  
- в статус выводится зелёное сообщение: «Загружено расписаний: N».

**FR.04.05. Применение данных из редактора**  
**FR.04.05.01.** Кнопка **«Применить одну дату»**:  
- читает содержимое текстового поля, пытается распарсить JSON.  
- проверяет, что полученный объект соответствует интерфейсу `ScheduleEntry` (обязательные поля `date` (строка YYYY-MM-DD), `schedule` (объект с `activities` – массив, каждый элемент соответствует `ActivityEntry`), а также наличие поля `current_datetime` (его значение при импорте игнорируется, но для валидации достаточно, чтобы поле существовало)).  
- если формат неверен – красное сообщение в статус, прерывание.  
- если формат верен, проверяет, существует ли уже расписание с такой же датой в `localStorage`.  
  - **Если дата отсутствует** – добавляет новую запись в массив `schedules`, затем выполняет сортировку массива по датам. При этом поле `current_datetime` импортированного объекта **игнорируется** – вместо него устанавливается текущее время в формате ISO 8601 с часовым поясом +03:00. Обновляет корневое `current_datetime` и сохраняет в `localStorage`. Сообщение: «Расписание для даты X добавлено».  
  - **Если дата уже есть** – показывает модальное окно с предупреждением: «Дата X уже существует. Перезаписать?» и кнопки «Да» / «Нет». При согласии выполняет замену существующего элемента, затем сортировку массива. Поле `current_datetime` импортированного объекта **игнорируется** – вместо него устанавливается текущее время. Обновляет корневое `current_datetime`. Сообщение: «Расписание для даты X перезаписано».  
- после успешного применения обновляется список дат (перерисовываются чекбоксы) и **чекбокс этой даты обязательно очищается** (снимается выделение).  
- **Примечание:** Проверка условия `delta === active + interruptBreaks + distractionBreaks` при импорте не выполняется; она осуществляется только при сохранении активностей в трекере (раздел 7.3).

**FR.04.05.02.** Кнопка **«Применить несколько дат»**:  
- читает содержимое текстового поля, парсит JSON.  
- проверяет, что полученный объект является массивом и каждый элемент соответствует `ScheduleEntry` (с полями `date`, `schedule` (с `activities`) и `current_datetime`). Поле `current_datetime` при проверке может быть любым, его значение всё равно будет перезаписано. Если нет – красное сообщение.  
- для каждой даты из массива проверяет наличие в текущем хранилище. Формирует два списка: **новые даты** (отсутствуют) и **существующие даты**.  
- если список существующих дат не пуст, показывает модальное окно с перечислением этих дат и вопросом: «Перезаписать существующие расписания для указанных дат?». Кнопки «Перезаписать все» и «Отмена».  
- при согласии (или если список существующих пуст) – объединяет данные:  
  - для новых дат – добавляет записи;  
  - для существующих – заменяет их.  
  При этом для каждой затронутой даты поле `current_datetime` **устанавливается на текущее время** (значение из импортированного JSON игнорируется).  
- после объединения выполняет сортировку массива `schedules` по датам, обновляет корневое `current_datetime`, сохраняет в `localStorage`, перерисовывает список дат.  
- выводит зелёное сообщение с **раздельным указанием**: «Добавлено дат: X (список: date1, date2...). Перезаписано дат: Y (список: date3, date4...)».  
- очищает все чекбоксы.

**FR.04.06. Дополнительные элементы управления**  
**FR.04.06.01.** Кнопка **«Очистить редактор»** – очищает текстовое поле.  
**FR.04.06.02.** Кнопка **«Обновить список дат»** – перечитывает `localStorage`, проверяет валидность, сортирует и перерисовывает таблицу чекбоксов (на случай внешних изменений).  
**FR.04.06.03.** Кнопка «Удалить выбранные расписания»:
располагается рядом с кнопками «Выбрать все» / «Сбросить все»;
при нажатии проверяет, что выбран хотя бы один чекбокс; иначе – сообщение об ошибке в статус (красное);
показывает модальное окно с подтверждением: «Вы действительно хотите удалить расписания для следующих дат: список_дат ?» и кнопками «Удалить» / «Отмена»;
при подтверждении удаляет выбранные записи из массива schedules корневого объекта, выполняет сортировку оставшихся дат, обновляет корневое `current_datetime`, сохраняет в localStorage, перерисовывает список дат;
выводит зелёное сообщение: «Удалено расписаний: N (даты: date1, date2...)»;
очищает все чекбоксы.

**FR.04.07. Валидация и сообщения**  
**FR.04.07.01.** Все ошибки и успешные операции выводятся в едином блоке статуса (зелёный/красный).  
**FR.04.07.02.** Для всех операций, изменяющих `localStorage`, обязательно обновляется поле `current_datetime` корневого объекта текущим временем в формате ISO 8601 с часовым поясом +03:00.  

**FR.04.08. Сортировка**  
**FR.04.08.01.** После любого изменения `localStorage` (добавление, удаление, перезапись, загрузка валидных данных из редактора) массив `schedules` в корневом объекте должен быть отсортирован по полю `date` по возрастанию (от старых дат к новым). Сортировка выполняется перед сохранением.  

**FR.04.09. Стилизация и технические требования**  
**FR.04.09.01.** Страница использует общий `main.css`. При необходимости допускается добавить специфичные стили в отдельный файл `import-export.css`.  
**FR.04.09.02.** Текстовое поле (`textarea`) должно иметь `resize: both`, моноширинный шрифт, начальную ширину 800px и высоту 400px (или заданные через CSS).  
**FR.04.09.03.** Список дат с чекбоксами может быть организован в виде колонок (flex или таблицы), но без адаптивности (фиксированная ширина страницы 2560px, полосы прокрутки).

## 05. Дневной трекер – отображение расписания и выбор даты (`daily-tracker.html`)

### 05.01. Назначение

Страница позволяет:
- **FR.05.01.01.** Отслеживать активности пользователя в течение дня с визуализацией на временной шкале.
- **FR.05.01.02.** Выбирать дату для просмотра расписания через специальный диалог (только из уже существующих расписаний).
- **FR.05.01.03.** Просматривать легенду рангов и категорий с цветовой индикацией.
- **FR.05.01.04.** Видеть текущее время в виде вертикальной линии на шкале (только для сегодняшней даты).

**Примечание:** редактирование, добавление, удаление активностей, перетаскивание блоков, управление пересечениями, шаблоны и JSON-редактор вынесены в разделы 06, 07, 08.

### 05.02. Загрузка и инициализация

**FR.05.02.01.** При открытии страницы код проверяет `localStorage` по ключу `time-tracker-categories`:
- Если данные есть и являются валидным JSON (согласно структуре `time-tracker.d.ts`), они загружаются и используются.
- Если данных нет или они невалидны – отображается блок с ошибкой конфигурации, работа страницы блокируется.

**FR.05.02.02.** Также из `localStorage` загружаются расписания по ключу `time-tracker-schedules` (если есть). Если нет – отображается сообщение «Нет сохранённых расписаний».

**FR.05.02.03.** По умолчанию после загрузки страницы:
- Текущая выбранная дата – сегодняшняя (YYYY-MM-DD).
- Если расписание на эту дату существует, оно отображается на временной шкале. При этом **поле `current_datetime` соответствующего `ScheduleEntry` должно быть обновлено на текущее время** (момент загрузки).
- Если расписание отсутствует, временная шкала пуста, а в блоке статуса выводится сообщение: «Расписания за сегодня ещё нет».

**FR.05.02.04.** При загрузке расписания для любой даты (выбор через календарь, кнопку «Выбрать день», кнопку «Сегодня», начальная загрузка страницы, а также при создании нового пустого расписания) поле `current_datetime` в соответствующем `ScheduleEntry` **должно быть установлено на текущее время** в формате ISO 8601 с часовым поясом +03:00. Это требование распространяется на все случаи обращения к расписанию (даже если оно не изменялось).

**FR.05.02.05.** При загрузке расписания для любой даты (в том числе при переключении дат) поле `current_datetime` в соответствующем `ScheduleEntry` **всегда обновляется на текущее время**, независимо от того, были ли изменения в активностях.

### 05.03. Верхняя панель управления датой

**FR.05.03.01.** В верхней части страницы располагаются две кнопки:
- **«Выбрать день»**
- **«Сегодня»**

**FR.05.03.02. Кнопка «Выбрать день»**:
- При нажатии открывается модальное окно.
- В модальном окне отображается список всех дат, для которых существуют расписания в `localStorage` (из массива `schedules` корневого объекта), отсортированный по возрастанию даты.
- Каждая дата сопровождается **радиокнопкой** (выбор только одной даты).
- Внизу окна расположены кнопки: **«Выбрать»** и **«Отмена»**.
- После выбора радиокнопки и нажатия «Выбрать»:
  - Выбранная дата становится текущей.
  - Расписание для этой даты загружается и отображается на временной шкале.
  - Поле `current_datetime` для этой даты обновляется на текущее время (см. FR.05.02.04).
  - Модальное окно закрывается.
- Если ни одна радиокнопка не выбрана, кнопка «Выбрать» неактивна или выводится сообщение об ошибке.

**FR.05.03.03. Кнопка «Сегодня»**:
- При нажатии текущей датой становится сегодняшняя (YYYY-MM-DD).
- Выполняется проверка: существует ли расписание на эту дату в `localStorage`.
- Если расписание существует – оно загружается и отображается на временной шкале, поле `current_datetime` обновляется текущим временем.
- Если расписание отсутствует – временная шкала очищается (становится пустой), а в блоке статуса выводится сообщение: «Расписания за сегодня ещё нет».

### 05.04. Отображение временной шкалы и блоков активностей

**FR.05.04.01.** Шкала расположена слева и идёт сверху вниз. Высота шкалы = 1440 пикселей (1 минута = 1 пиксель). На шкале отображаются:
- Метки каждого часа (например, «00:00», «01:00» … «23:00») с тонкой линией.
- Тонкие деления каждые 5 минут (необязательно, но желательно).
- Горизонтальная линия текущего времени (только для сегодняшней даты) с меткой времени в формате `HH:MM`.

**FR.05.04.02. Блок активности**:
- **Ширина** блока фиксирована – **500 пикселей**.
- **Верхняя граница** = `start` (минут от полуночи) в пикселях.
- **Высота** = `delta` (минут) в пикселях.
- **Цвет фона**: цвет категории (с учётом наследования от ранга).
- **Цвет текста** – контрастный (чёрный или белый, вычисляется динамически на основе фона).
- Внутри блока отображается:
  - время начала и окончания (`start` – `end`),
  - длительность в формате `ЧЧ:ММ`,
  - название активности (из справочника по `activityTypeId`),
  - при наличии комментария – иконка 💬 и текст комментария.
- Если активности накладываются друг на друга (их временные интервалы пересекаются), то блоки, начинающиеся позже, сдвигаются вправо. Количество колонок определяется автоматически. Контейнер блоков расширяется по горизонтали, полосы прокрутки возникают у всей страницы, если содержимое не помещается.

**FR.05.04.03. Визуализация статуса**:
- `done` – блок полупрозрачный, серая гамма (`opacity: 0.6`, `filter: grayscale(0.4)`), в правой части блока отображается галочка «✓».
- `in_progress` – блок с пунктирной рамкой (`border: 2px dashed #f59e0b`).
- `planned` – обычный вид (без дополнительных эффектов).

**FR.05.04.04. Текущее время**:
- Для сегодняшней даты на шкале отображается горизонтальная линия ярко-синего цвета на высоте, соответствующей текущему времени (в минутах от полуночи).
- Линия сопровождается меткой времени (например, «14:30») в левой части - на том же уровне, где находятся метки шкалы. 
- Линия обновляется каждую минуту в 00 секунд и при перезагрузке страницы.

### 05.05. Легенда

**FR.05.05.01.** Под временной шкалой отображается легенда, которая включает:
- Все ранги из справочника с их цветом и коэффициентом.
- Для каждого ранга – список его категорий с цветом (собственным или унаследованным от ранга).

**FR.05.05.02.** Легенда помогает быстро идентифицировать тип активности по цвету блока.

### 05.06. Технические требования (отображение)

**FR.05.06.01.** Все статические стили (CSS) вынесены в отдельный файл `daily-tracker.css` (используется общий `main.css` для базовых элементов и специфичные стили для трекера).

**FR.05.06.02.** Вёрстка рассчитана на большой экран с возможностью горизонтальной прокрутки (если колонки активностей не помещаются). При нехватке места по вертикали появляется вертикальная прокрутка всей страницы.

**FR.05.06.03.** Запрещается использование медиа-запросов, адаптивной вёрстки (резиновость) – только фиксированные размеры.

**FR.05.06.04.** Данные для отображения берутся из:
- Справочника активностей – ключ `time-tracker-categories` в `localStorage`.
- Расписаний – ключ `time-tracker-schedules` в `localStorage`.

**FR.05.06.05.** При отсутствии или невалидности справочника страница блокируется и отображает сообщение об ошибке. При отсутствии или невалидности расписаний – отображается пустая шкала с соответствующим сообщением.

## 06. Дневной трекер – добавление и редактирование активностей (`daily-tracker.html`)

### 06.01. Добавление новой активности

**FR.06.01.01.** В верхней панели страницы располагается кнопка **«+ Добавить»**.

**FR.06.01.02.** При нажатии на кнопку «+ Добавить» открывается модальное окно с заголовком **«Редактирование активности»**. Эта же форма используется как для создания новой активности, так и для редактирования существующей.

**FR.06.01.03.** Модальное окно содержит:
- Выбор ранга (загружается из справочника).
- Выбор категории (зависит от выбранного ранга).
- Выбор типа активности (зависит от выбранной категории).
- Поле комментария.
- **Группа из трёх кнопок для выбора статуса** (западающие кнопки / toggle‑кнопки):
  - «Запланировано» (planned)
  - «Выполняется» (in_progress)
  - «Сделано» (done)
  Функционально кнопки работают как радиокнопки: активной может быть только одна из трёх; при нажатии на неактивную кнопку она становится активной, а предыдущая активная отжимается.
- Поля «Дельта», «Активное время», «Перерывы из-за прерываний», «Перерывы из-за отвлечений».
- Поля «Начало» и «Конец» в формате `HH:MM` (при сохранении преобразуются в минуты).
- Кнопки:
  - **«Начать»** – устанавливает время начала равным текущему моменту (с округлением до 1 минуты), переводит статус в «Выполняется» и корректирует время окончания, сохраняя текущую дельту.
  - **«Сделано»** – устанавливает время окончания равным текущему моменту (с округлением до 1 минуты), переводит статус в «Сделано», пересчитывает дельту (delta = end - start)
  - **«Сохранить»** – сохраняет активность (новую или изменения) после прохождения валидации.
  - **«Отмена»** – закрывает модальное окно без сохранения.

**FR.06.01.04.** При создании новой активности поля формы заполняются значениями по умолчанию: начало – текущее время (округлённое до 1 минуты), конец – начало + 1 час, статус – «Запланировано».

**FR.06.01.05.** После сохранения новая активность добавляется в расписание текущего дня, данные сохраняются в `localStorage`, временная шкала перерисовывается. При этом **поле `current_datetime` для текущего дня (в `ScheduleEntry`) обновляется на текущее время**.

### 06.02. Редактирование существующей активности

**FR.06.02.01.** **Двойной клик** по любому блоку активности на временной шкале открывает модальное окно редактирования с заголовком **«Редактирование активности»** (та же самая форма, что и для добавления).

**FR.06.02.02.** Все поля формы заполняются текущими значениями выбранной активности.

**FR.06.02.03.** В окне редактирования дополнительно присутствует кнопка **«Удалить»**, позволяющая удалить активность из расписания.

**FR.06.02.04.** После сохранения изменений (или удаления) данные обновляются в `localStorage`, временная шкала перерисовывается, модальное окно закрывается. При этом **поле `current_datetime` для текущего дня обновляется на текущее время**.

**FR.06.02.05.** При редактировании действуют те же правила валидации, что и при создании (проверка условий: `delta === end - start` и `delta === active + interruptBreaks + distractionBreaks`).


## Раздел 06.03. Правила валидации значений перед сохранением активности

### Бизнес-правила
- После валидации активное время active в минутах должно быть строго больше нуля. Активность, в которой пользователь не выполнял полезных действий (только перерывы), не имеет смысла и не должна сохраняться. Это правило применяется как при ручном вводе, так и после всех корректирующих диалогов.
- В текущем прототипе поле «Перерывы из-за прерываний» (interruptBreaks) доступно для ручного редактирования. Это временное решение для тестирования. В финальной версии поле будет удалено из интерфейса, а его значение будет вычисляться автоматически на основе пересечений типов interrupt overlap. В логике валидации (раздел 06.03) пока оставляем возможность редактирования, но в диалогах Случая 2, шаг 2, не добавляем вариант изменения interruptBreaks, так как в будущем оно станет вычисляемым.
- Флаги *Changed указывают на то, изменял ли пользователь соответствующее поле в форме. При валидации система может перезаписывать любые поля, если это необходимо для приведения данных к корректному виду.
- Цель валидации - не предотвратить ошибки пользователя, а обеспечить консистентность данных. Если пользователь ошибся при редактировании и нажал сохранить, но данные оказались консистентными - валидация будет успешно пройдена.

### Оболочка функции

```javascript
/**
 * Валидация активности перед сохранением.
 * @param {Object|null} oldAct — старая активность (null для новой)
 * @param {Object} newAct — новые значения (поля start, end, delta, active, interruptBreaks, distractionBreaks)
 * @returns {Promise<Object|null>} — возвращает скорректированный newAct или null при отмене
 */
async function validateAndFix(oldAct, newAct) {
    // Проверка границ и базовых условий
    if (newAct.start < 0 || newAct.start > 1440 ||
        newAct.end < 0 || newAct.end > 1440 ||
        newAct.delta < 0 || newAct.delta > 1440 ||
        newAct.active < 0 || newAct.active > 1440 ||
        newAct.interruptBreaks < 0 || newAct.interruptBreaks > 1440 ||
        newAct.distractionBreaks < 0 || newAct.distractionBreaks > 1440) {
        // диалог с сообщением "Некорректные значения времени или перерывов. Исправьте."
        // единственная кнопка "Вернуться к редактированию"
        return null;
    }
    
    // 1. Проверка двух обязательных условий
    const timeRuleOk = (newAct.delta === newAct.end - newAct.start);
    const compositionRuleOk = (newAct.delta === newAct.active + newAct.interruptBreaks + newAct.distractionBreaks && newAct.delta > 0 && newAct.active > 0);
    
    // 2. Если оба правила соблюдены — возвращаем newAct без изменений
    if (timeRuleOk && compositionRuleOk) {
        return newAct;
    }
    
    // 3. Определяем, какие поля были изменены (для новых активностей считаем, что всё изменено)
    // Для новой активности (oldAct === null) все флаги изменений устанавливаются в true, чтобы применить полную валидацию ко всем полям.
    let startChanged = true;
    let endChanged = true;
    let deltaChanged = true;
    let activeChanged = true;
    let intChanged = true;
    let distChanged = true;    
    if (!(oldAct === null)) {
        startChanged = oldAct.start !== newAct.start;
        endChanged   = oldAct.end !== newAct.end;
        deltaChanged = oldAct.delta !== newAct.delta;
        activeChanged = oldAct.active !== newAct.active;
        intChanged   = oldAct.interruptBreaks !== newAct.interruptBreaks;
        distChanged  = oldAct.distractionBreaks !== newAct.distractionBreaks;
    }

    
    // 4. Разветвление по случаям (будет добавлена полная логика из таблиц решений)
    //    Случай 1, Случай 2
    
    // Если ни один случай не применился (защита от ошибок), возвращаем newAct
    return newAct;
}
```

## 07. Дневной трекер – перетаскивание блоков (`daily-tracker.html`) – Финальная версия

**FR.07.01.** Функционал перетаскивания должен быть реализован по аналогии с **Google‑календарём в представлении «День»**: при зажатии левой кнопки мыши на блоке активности и движении вверх/вниз блок перемещается целиком, а его время начала и окончания синхронно изменяются.

**FR.07.02. Область действия**  
Перетаскивание доступно **только для десктопных браузеров** (разрешение экрана 2560px, управление мышью). Сенсорные устройства не поддерживаются.  
Перетаскивание применяется только к блокам активностей, у которых статус **не равен `done`**. Блоки со статусом `done` не реагируют на перетаскивание.

**FR.07.03. Семантика перетаскивания**  
- При перетаскивании **длительность (`delta`), а также поля `active`, `interruptBreaks`, `distractionBreaks` остаются неизменными** – сдвигается только временной интервал (одновременно `start` и `end`).  
- Шаг изменения времени – **1 минута** (благодаря масштабу: 1 минута = 1 пиксель на временной шкале). Округление не требуется.

**FR.07.04. Визуальное поведение**  
- Во время перетаскивания блок **визуально следует за курсором** (его положение обновляется в реальном времени).  
- Дополнительные визуальные эффекты (полупрозрачность, тень, смена курсора) **не требуются**.

**FR.07.05. Ограничения по границам дня**  
- `start` не может стать меньше 0.  
- `end` не может превышать 1440.  
- При попытке сдвинуть блок выше 00:00 он **прилипает** к верхней границе (`start = 0`, `end = delta`).  
- При попытке сдвинуть блок ниже 24:00 он **прилипает** к нижней границе (`end = 1440`, `start = 1440 - delta`).

**FR.07.06. Алгоритм перемещения**  

1. **Начало перетаскивания** (`mousedown` на блоке):  
   - Запомнить исходные `start` (`originalStart`) и `end` (`originalEnd`) активности.  
   - Запомнить начальную координату мыши `startClientY` (в пикселях от верха окна).  
   - Установить глобальный флаг `isDragging = true` (например, в замыкании модуля).  

2. **Во время движения** (`mousemove`):  
   - Если `isDragging === false` – ничего не делать.  
   - Вычислить смещение: `deltaY = currentClientY - startClientY` (пиксели).  
   - `deltaMinutes = deltaY` (1 пиксель = 1 минута).  
   - Вычислить новые значения:  
     `newStart = originalStart + deltaMinutes`  
     `newEnd = originalEnd + deltaMinutes`  
   - Применить правила прилипания к границам дня (FR.07.05).  
   - **Визуально сместить блок** (например, через `transform: translateY(...)`), не сохраняя данные в `localStorage`.  

3. **Завершение перетаскивания** (`mouseup`):  
   - Если перетаскивание было отменено (см. FR.07.08) – вернуть блок в исходное положение и не сохранять.  
   - Иначе вычислить итоговые `newStart`, `newEnd`, применив те же **правила прилипания к границам дня** (FR.07.05).  
   - Если `newStart === originalStart` – ничего не делать.  
   - Иначе создать объект `newAct` с обновлёнными `start`, `end`, `delta` (остаётся прежней), `active`, `interruptBreaks`, `distractionBreaks` (без изменений).  
   - Вызвать функцию валидации `validateAndFix(oldAct, newAct)` (см. раздел 06.03).  
     - Если валидация возвращает `null` (пользователь нажал «Вернуться к редактированию»), то **открыть модальное окно редактирования** для этой активности (как при двойном клике) и отменить перетаскивание.  
     - Если валидация возвращает скорректированный объект (с возможными изменениями `active` или перерывов), использовать его для сохранения.  
   - Сохранить изменения в `localStorage` через `saveToLocalStorage()`.  
   - Обновить поле `current_datetime` для текущей даты (вызвать `updateScheduleCurrentDateTime(currentDate)`).  
   - Перерисовать временную шкалу (`renderActivities()`).  
   - Сбросить флаг `isDragging`.

4. **Сброс и очистка**:  
   - Отключить обработчики `mousemove`/`mouseup` после завершения.  
   - Удалить временные визуальные стили.

**FR.07.07. Обработчики событий**  
- Используются только события мыши: `mousedown`, `mousemove`, `mouseup`.  
- События `touchstart`/`touchmove`/`touchend` **не реализуются**.  
- На время перетаскивания необходимо отключать стандартное поведение браузера (выделение текста, перетаскивание изображений) через `preventDefault()` на `mousedown` и `mousemove`.  
- Двойной клик (`dblclick`) для открытия редактора не должен срабатывать, если начато перетаскивание (использовать флаг `isDragging`).

**FR.07.08. Отмена перетаскивания**  
- Клавиша **Esc** – при нажатии во время перетаскивания отменяет перемещение: блок возвращается в исходное положение, данные не сохраняются, флаг сбрасывается.  
- Если курсор мыши отпущен вне области трекера (например, на фоне страницы), перетаскивание также отменяется без сохранения.  
- Потеря захвата (например, при переключении вкладок) обрабатывается как отмена.

**FR.07.09. Взаимодействие с другими функциями**  
- После успешного перемещения (и сохранения) автоматически перерисовываются все блоки, и может измениться их расположение по колонкам (функция `calculateColumns`) – это допустимо.  
- Если валидация (раздел 06.03) предлагает варианты исправления и пользователь выбирает какой-либо из них, то после сохранения блок отображается с новыми значениями. Если пользователь нажимает «Вернуться к редактированию», то открывается форма редактирования активности (как при двойном клике), а исходное перетаскивание отменяется.

**FR.07.10. Технические требования к реализации**  
- Код перетаскивания добавляется в `daily-tracker-render.js` (функция `renderActivities` должна навешивать обработчики на каждый блок).  
- Глобальное состояние перетаскивания (`isDragging`, `originalStart`, `originalEnd`, `startClientY`) хранить в замыкании модуля или в отдельном объекте в `daily-tracker-core.js`.  
- Для визуального смещения использовать `transform: translateY(...)`, чтобы не влиять на layout.  
- После вызова `validateAndFix`, если она вернула `null`, необходимо открыть модальное окно редактирования (вызвать `openEditModal` с текущей активностью). При этом перетаскивание считается отменённым.
